# 배경 — "한 세션 공유"에서 "기기를 도구로"까지

이 문서는 이 저장소가 어떤 필요에서 시작했고, 어떤 가정이 실행해 보니 틀렸으며, 어떻게 지금의 구조에 이르렀는지를 순서대로 적는다. 숫자는 모두 2026-10-08~09 에 내 맥 세 대에서 잰 값이고, 비용은 API 단가로 환산했다.

## 1. 환경

나는 맥 세 대를 쓴다. 문서에서는 실제 이름 대신 다음처럼 부른다.

| 이름 | 기기 | 역할 |
|---|---|---|
| `laptop` | M5 Max 128GB | 지휘. 내가 앉아서 일하는 기기 |
| `homemac` | M3 Max 64GB | 집에서 상시 켜져 있음 |
| `air` | M2 8GB | 가벼운 기기 |

세 대는 Tailscale 로 묶여 있고, ssh 키 인증과 ssh 별칭으로 서로 접속한다. 터미널은 cmux 를 쓴다. 각 맥에 떠 있는 GUI cmux 를 소켓 비밀번호로 원격 조종할 수 있어서, 다른 맥의 cmux 브라우저를 원격으로 부릴 수 있다. 또 `~/.claude` 를 Syncthing 으로 맥끼리 동기화하고 있어서, 노트북에서 쌓인 세션 기록(.jsonl)이 홈맥에도 있다. 이 마지막 사실이 나중에 중요해진다.

## 2. 고통: 한 기기에 몰린 일

나는 노트북 한 대에 Claude Code 프로세스를 100개 넘게 띄워 두고 운용한다. 평소에는 128GB 로 버틴다. 문제는 무거운 일이 겹칠 때였다.

영상 렌더 워커 8개(약 9GB)는 그것만으로는 안전했다. 그런데 같은 기기에서 병렬 `claude -p` 여러 개를 함께 돌리자 메모리가 버티지 못했고, 커널 패닉이 났다. 이런 일을 두 번(2026-06-19, 2026-09-27) 겪었다.

그동안 집의 64GB 맥과 맥북에어는 거의 놀고 있었다. 메모리가 모자란 게 아니라, 한 기기에 몰려 있었던 것이다.

## 3. 출발점: OpenRig 를 읽다가 생긴 질문

그 무렵 공개 오픈소스 [OpenRig](https://github.com/mvschwarz/openrig)를 분석하고 있었다. OpenRig 는 Claude Code·Codex 세션 여러 개를 tmux 위에 팀으로 상주시키는 데몬이다. 그걸 읽다가 이런 질문이 생겼다.

> 맥 세 대가 Claude Code 세션 하나를 실시간으로 같이 쓰면서 일을 나눠 맡을 수 있나? 각자 RAM 을 따로 쓰면서, 어떤 기기는 브라우저 조작, 어떤 기기는 다른 일을.

OpenRig 를 그대로 들여오지는 않았다. 이유는 네 가지였다.

- **모델이 다르다.** OpenRig 는 "세션 여러 개 = 팀"이다. 나는 세션 하나에 일을 나눠 주고 싶었다.
- **설치하면 사용자의 Claude 설정 폴더에 쓴다.** 나는 그 폴더를 여러 맥에 동기화하고 있어서 건드리고 싶지 않았다.
- **메모리 상한이 없다.** 내 문제가 바로 메모리였다.
- **아직 1.0 이전이다.**

대신 패턴은 빌렸다. 판정 시점의 증거를 해시로 고정해 두고, 증거가 바뀌면 판정을 무효로 만드는 "증거 동결"이 대표적이다. 이 패턴은 나중에 verify 도구가 됐다.

## 4. 판정: 말로 하지 않고 실행해서

질문을 몇 갈래로 나누고, 각각 실제로 돌려서 판정했다.

### 4-1. 세 기기가 같은 세션을 동시에 진행할 수 있나 — 불가

Claude Code 세션은 한 프로세스가 기록 파일 하나에 이어 쓰는 구조다. 두 기기가 같은 세션을 동시에 이어 쓰면 기록이 갈라진다. 이건 우회할 수 있는 제약이 아니라 구조 자체였다. 첫 번째 가정은 여기서 무너졌다.

### 4-2. 그렇다면 무엇이 RAM 을 먹는가

여기서 관점이 바뀌었다. Claude 의 추론은 서버에서 돈다. 기기의 RAM 을 먹는 것은 claude 프로세스 자체보다, 그 세션이 부리는 **도구**였다. 브라우저, 빌드, 렌더, 대량 스캔 같은 것들이다.

그렇다면 나눠야 할 것은 대화가 아니라 실행이다. 세션은 하나로 두고, 무거운 실행만 다른 기기로 보내면 된다.

### 4-3. 다른 기기의 셸·브라우저를 부릴 수 있나 — 된다

`mm` 이라는 셸 래퍼를 만들었다. `mm homemac run "…"` 은 홈맥 셸에서 명령을 실행하고, `mm air read-url …` 은 에어의 cmux 브라우저로 페이지를 열어 본문을 읽고 탭을 닫는다. 원격 셸 실행은 0.2초 걸렸다. ssh 를 매번 새로 접속하면 왕복 0.2~0.3초였는데, ControlMaster 로 연결을 재사용하자 0.04초가 됐다.

### 4-4. 대화 맥락을 통째로 다른 기기에 복제하면 — 되지만 비싸다

두 번째 가정은 "맥락이 필요한 일은 분신(fork)을 보내면 된다"였다. 세션 기록이 이미 Syncthing 으로 홈맥에 와 있으니, 홈맥에서 그 세션을 복제해 이어 묻는 것이다.

실제로 됐다. 내가 OpenRig 분석을 해 온 세션(약 26만 토큰)을 홈맥에서 복제했더니, 파일을 읽지 않고 대화 맥락만으로 분석 결론을 요약했다. 문제는 값이었다. 한 번에 $2.14, 약 10초였다.

같은 일을 다르게 해 봤다. 지휘 세션이 결론에 필요한 것만 약 1,000자 브리프로 쓰고, 설정을 비운 가벼운 Haiku 작업자에게 넘겼다. 결과는 같은 내용으로 정확했고, $0.0146·5.5초였다. 약 147배 쌌다. 분신은 기본이 아니라 최후 수단으로 내려갔다.

### 4-5. 작업자는 얼마나 가벼워질 수 있나

원격 작업자를 기본 구성으로 띄우면, 전역 CLAUDE.md·메모리·스킬·MCP 도구 정의가 전부 실린다. 같은 단순 작업에 맥락이 95,209 토큰, $0.3119 였다. 빈 설정 디렉터리에 도구를 줄인 가벼운 구성으로 바꾸자 26,934 토큰, $0.0283 이 됐다. 같은 작업자에게 이어서 일을 시키면 새로 쓰는 캐시가 225 토큰뿐이었다.

더 가볍게 하려고 `--bare` 최소 모드를 시험했지만, 구독 로그인으로는 쓸 수 없었다. API 키 전용이다. 세 번째 가정도 여기서 접었다.

### 4-6. 기기마다 대리인 에이전트를 두면 — 대리인이 비용이다

네 번째 가정은 "기기마다 에이전트를 하나씩 붙여 동시에 돌리면 된다"였다. Claude Code 의 Workflow 로 기기 하나당 대리인 하나를 두고 세 기기에 일을 나눴다. 동작은 했지만 36초가 걸렸고, 대리인 셋이 쓴 토큰이 약 22만이었다. 대리인마다 기본 맥락을 다시 싣기 때문이다.

같은 분배를 `mm batch` 한 번으로 바꾸자 6.2초, 대리인 토큰 0 이 됐다. 단순히 세 기기에 명령을 뿌리는 batch 는 0.9초였다.

### 4-7. 기기 간에 프롬프트 캐시가 공유되나 — 미검증

분신 시험에서 홈맥은 캐시를 두 번 모두 새로 썼다. 기기마다 claude 버전이 달라서 시스템 프롬프트가 달라졌다는 가설을 세웠지만, 확인하지 않았다. 분신을 최후 수단으로 내렸기 때문에 우선순위가 낮다.

## 5. 이름 붙이기: 기기를 도구로

여기까지 오자 그림이 정리됐다. 세션은 하나다. 남는 기기는 그 세션의 **MCP 도구**로 등록한다. Claude 입장에서는 Read·Bash 옆에 도구가 몇 개 늘어난 것뿐이다. 나는 이걸 **기기를 도구로(Machines as Tools)** 라고 부르고, 한 줄로 줄이면 이렇다.

> 에이전트를 늘리기 전에, 기기를 도구로.

`mm` 을 정본으로 두고, 그 위에 MCP 서버 `multimac` 을 얇게 씌웠다. 처음에는 기본 도구 8개(status·run·read_url·browser·close_tab·ask·fork·batch)였다.

## 6. 실전으로 확인

추상적인 데모만으로는 부족해서, 내가 실제로 했던 일 하나를 축약해 다시 해 봤다. 최근 세션 기록에서 개인 사이드 프로젝트 후보를 발굴하는 일이다(프로젝트 이름은 공개하지 않는다).

| 단계 | 도구 | 시간 |
|---|---|---|
| 세션 기록 535개(2GB) 전수 스캔 | homemac 셸 (LLM 0) | 3.3초 |
| 공개 프로필 페이지 읽기 | air 브라우저 (LLM 0) | 7.4초 |
| 후보를 나눠 카드 작성, Haiku 작업자 3개 동시 | homemac 작업자 | 23초 |
| 카드 병합 · 같은 프로젝트 묶기 · 선정 | 지휘 세션 | — |

전체 43초, 작업자 비용 $0.226 이었다. 후보 15개에서 카드 5장, 최종 프로젝트 3개가 나왔다. 홈맥에 세션 기록이 이미 동기화돼 있었기 때문에 가능한 일이었다.

## 7. 도구를 늘리기

기본 도구가 안정되자 일 단위 도구 다섯 개를 더 만들었다. render(렌더를 홈맥으로), verify(증거 동결 판정 장부), mine(세션 기록 발굴), research(레포 조사 팬아웃), auto(능력 이름으로 자동 배정)다.

만드는 방식도 이 원칙을 따랐다. 도구마다 "만드는 에이전트"와 "맥락을 공유하지 않는 검증 에이전트"를 짝지어 Workflow 로 동시에 돌렸다. 만드는 에이전트 5개, 검증 에이전트 5개였고 다섯 도구 모두 검증을 통과했다. MCP 도구는 8개에서 19개가 됐다. 이 저장소의 71초 컨셉 영상도 그중 render 도구로 홈맥에서 렌더했다.

## 8. 실패한 가정 정리

| 처음 가정 | 실행해 보니 | 지금 |
|---|---|---|
| 세 기기가 한 세션을 같이 진행할 수 있다 | 세션은 한 프로세스가 기록 하나에 이어 쓰는 구조라 불가 | 세션은 하나, 기기는 도구 |
| 맥락이 필요하면 대화를 통째로 복제하면 된다 | 26만 토큰 세션 복제 $2.14 | 브리프 + Haiku $0.0146, 복제는 최후 수단 |
| 기기마다 대리인 에이전트를 붙이면 된다 | 36초 · 대리인 토큰 약 22만 | `mm batch` 6.2초 · 대리인 토큰 0 |
| `--bare` 로 작업자를 최소화할 수 있다 | 구독 로그인 불가(API 키 전용) | 빈 설정 디렉터리 + 도구 축소 |
| 기기 간 프롬프트 캐시가 재사용될 것이다 | 두 번 모두 새로 씀 | 미검증 (버전 차이 가설) |
| 싼 모델 판정 한 번이면 충분하다 | 같은 입력에 Haiku 가 fail/pass 로 갈림 | 중요한 판정은 Sonnet 또는 2회 |
