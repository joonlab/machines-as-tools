# 레시피 — 작업 추가 · 도구 추가 · 하루 운용

원칙을 실제 일에 적용하는 순서다. 원칙 자체는 [principles.md](principles.md), 도구별 설명은 [catalog.md](catalog.md)에 있다.

## 1. 작업 추가 레시피 (6단계)

새 일을 받았을 때 지휘 세션이 하는 순서다. 여섯 단계가 batch 두세 번으로 끝난다.

1. **쪼갠다 — 컨텍스트 경계로.** "구현·테스트·리뷰"가 아니라 "무엇을 읽고 무엇을 판단하나"로 나눈다. 읽기는 나누고 쓰기는 모은다.
2. **등급을 매긴다 — T0~T3.** 각 조각에 비용 사다리 단계를 붙인다. T0 가 많을수록 싸고 빠르고 재현된다.
3. **능력에 배정한다.** heavy · judge · browser. 보내기 전에 `status` 로 메모리 여유를 확인한다. 기기를 고르기 싫으면 `auto_dispatch` 에 능력 이름만 준다.
4. **브리프를 쓴다.** 판단 조각(T1·T2)이 있으면 배경을 한 장으로 쓴다. 여러 작업자가 같은 브리프를 같이 쓴다.
5. **batch 로 보낸다.** 같은 단계의 조각은 한 번에 보낸다. 앞 단계 결과가 다음 단계 입력이면 단계 사이에서만 기다린다.
6. **지휘 세션이 합친다 — 그리고 trace.** 중복을 묶고, 한계를 적고, 결정은 여기서 한다. 되돌릴 수 없는 마무리(발송·삭제·게시)도 여기서만 한다.

### 실전 예: 최근 세션 기록에서 개인 사이드 프로젝트 후보 찾기

실측 전체 43초, 작업자 비용 $0.226. 후보 15 → 카드 5 → 프로젝트 3.

```text
# 1차 batch — T0 두 개를 동시에
batch  scan     heavy    run       "세션 기록 535개(2GB) 스캔 → 후보 15"   # T0 · 3.3초
       profile  browser  read_url  "<공개 프로필 페이지>"                   # T0 · 7.4초

# 2차 batch — T1 세 개를 동시에, 같은 브리프를 공유
batch  cards1..3  judge  ask -m haiku -b brief.md "후보 5개씩 카드로"       # T1 × 3 · 동시 23초

# 지휘 세션
카드 병합 → 같은 프로젝트 묶기 → 최종 3개                                   # 결정은 지휘 세션에서
```

여기서 지휘 세션이 받은 것은 카드 제목과 파일 경로뿐이다. 카드 원문은 홈맥 파일로 남았다(원칙 4).

## 2. 도구 추가 레시피 (4단계)

"기기를 도구로"가 범용인 이유다. 셸 명령 하나로 할 수 있는 능력이면 무엇이든 도구가 된다.

1. **능력 하나를 셸 명령으로.** 예: 원격 GPU 렌더 = `ssh gpu "python render.py"`. 사람이 터미널에서 되는지부터 확인한다. 그 기기에서 그 명령이 정말 도는지가 첫 관문이다.
2. **`mm` 에 서브명령으로.** 호스트·인자를 검증하고, 출력 길이를 제한하고, 실패하면 짧은 오류를 낸다. 위험한 인자는 형식으로 막는다. 예: 탭 닫기는 `surface:N` 형식만 받는다.
3. **MCP 도구로 등록.** 도구 설명이 곧 라우팅 규칙이다. **"언제 쓰는지 · 언제 쓰지 않는지 · 얼마나 드는지"**를 설명에 적는다. Claude 는 그걸 읽고 고른다.
4. **`status` 에 얹는다.** 새 도구의 상태(살아 있나·여유 있나)를 한 줄로 보여 준다. 보내기 전에 판정할 수 있어야 도구다.

### 지금 있는 도구

| 도구 | 능력 | 상태 | 실측 (2026-10-09) |
|---|---|---|---|
| 홈맥 셸 · 가벼운 작업자 | heavy · judge | 구현 | 세션 535개 스캔 3.3초 · 작업자 회당 1~9센트 |
| 에어 cmux 브라우저 | browser | 구현 | 페이지 읽고 탭 닫기 2~7초 |

**다섯 도구를 한 번에 만든 방법도 이 원칙 그대로다.** 도구마다 "만드는 에이전트 → 맥락을 공유하지 않는 검증 에이전트"로 묶어 Workflow 로 동시에 만들었다(만드는 에이전트 5 + 검증 에이전트 5). 새 도구는 `mm` 을 고치지 않고 기본 동작(run·ask·batch·read-url)을 조합했다. 다섯 개 모두 검증을 통과했고, MCP 도구는 8개에서 19개가 됐다.

## 3. 하루 운용 예시

"세 대를 쓰는 느낌"은 기기를 의식하지 않을 때 난다. 말로 시키면 능력이 알아서 붙는다.

| 때 | 시키는 말 | 무엇이 붙나 |
|---|---|---|
| 아침 | **"지난주 세션 기록 정리해 줘"** | heavy 가 기록 전수 스캔(T0), judge 셋이 묶음별 요약(T1), 지휘 세션이 주간 정리 초안으로 합친다. → `mine_sessions` |
| 오전 | **"이 레포 써 볼 만한지 봐 줘"** | heavy 가 클론·집계(T0), browser 가 README·릴리스 페이지 읽기(T0), judge 가 요약(T1), 지휘 세션이 판단(T2 는 지휘 자신). → `research_repo` |
| 오후 | **앱 개발** | 편집은 노트북에서, 테스트·빌드는 heavy 로, 결과물 판정은 다른 모델의 judge 로. 생성자와 검증자를 싸게 분리한다. → `run` + `verify_judge` |
| 저녁 | **영상 렌더** | render 도구로 홈맥에 보내고 노트북은 계속 Claude 작업을 한다. 무거운 일이 한 기기에서 겹치지 않는다. → `render_check` → `render_remote` |
| 상시 | **로그인된 사이트** | browser 도구(에어)에 로그인 세션을 상주시킨다. 노트북 cmux 탭이 쌓이지 않는다. → `read_url` / `browser` |

### 이렇게 말하면, 이 도구가 붙는다

| 말 | 붙는 도구 |
|---|---|
| "지난주 내가 한 영상 작업 정리해 줘" | `mine_sessions` → 지휘 세션이 정리로 합침 |
| "이 레포 써 볼 만한지 봐 줘" | `research_repo` → 필요하면 `ask` 로 축별 심화 |
| "이 영상 렌더해 줘" (노트북이 바쁠 때) | `render_check` → `render_remote` |
| "이 보고서 수치 맞는지 다른 눈으로 봐 줘" | `verify_judge` (Sonnet) → 내보내기 직전 `verify_check` |
| "이 페이지들 읽고 요약해 줘" | `batch`[`read_url` × N] → `ask` Haiku + 브리프 |
| "무거운 거 알아서 돌려 줘" | `auto_dispatch`("heavy", …) |
